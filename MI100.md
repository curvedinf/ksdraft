# Running ksdraft on the MI100 server

Operational guide for training the Flint draft on the 4x MI100 machine
(gfx908, 32 GB each, XGMI full mesh). Design context: RESEARCH.md Sections
8-12; the machine also serves the int8-vllm recipes — training sessions are
dedicated (serving pauses), per the standing decision.

## Environment

The training environment mirrors the dev-box (`rocm7` pyenv env) with the
MI100 stack pins from the int8-vllm fork:

- torch (rocm build; the fork's serving venv pins `2.11.0+rocm7.1` — the
  training env may track it or the dev box's `2.10.0+rocm7.0`; keep kernels
  version-tolerant and validate on the server)
- triton (fork pin: 3.6.0; dev box runs 3.7.1 — same caveat)
- `ksdraft` installed editable from this repo: `pip install --no-build-isolation -e ".[dev]"`
- The Rosa credit engine: `git clone
  https://github.com/xiaoiecc/qkv-rosa-fast-exact-backward` as a sibling of
  this repo (default discovery: `~/Projects/qkv-rosa-fast-exact-backward`,
  override with `KSDRAFT_ROSA_CREDIT_REPO`), then
  `cd qkv-rosa-fast-exact-backward/conv_rosa_transformer && python build.py`
- `PYTORCH_ROCM_ARCH=gfx908` for any kernel work compiled on the server

Dev box (RX 7900 XTX, gfx1100) is the correctness testbed; ALL performance
numbers come from MI100 (the gfx1100/gfx908 int8 `tl.dot` lowering differs —
RESEARCH.md Section 10).

## Memory budget (Section 10)

| Per GPU (of 32 GB) | |
| --- | --- |
| PTQR INT8 Flint teacher (TP4, in-process) | ~10 GB |
| ksdraft draft training (masters + optimizer + activations) | ~13.5-15.5 GB |
| **Total** | **~24-26 GB** — fits with activation headroom |

Knobs if tight: FP16 masters (−2 GB), 8-bit Adam states (−4-6 GB), gradient
checkpointing.

## Testing ladder (run in this order after any stack change)

1. `pytest tests/ -q` — 55 CPU/GPU tests incl. reference parities
   (k-splanifolds KS3/KS3Int8, the Rosa credit engine at atol=0)
2. `ksdraft gate --config configs/flint.yaml --device cuda --out runs/gate`
   — dtype-tier battery (param budget, identity-init, bf16 parity, INT8 KS3
   modes, forward finiteness); must PASS before training
3. Trainer smoke: `ksdraft train --config configs/flint.yaml --stage warmup
   --device cuda --steps 40 ...` (synthetic corpus) — loss must decrease
4. Stage runs (below)

## Training stages (RESEARCH.md Section 11)

```bash
# Stage 0 — architecture warm-up (teacher-free; raw corpus)
ksdraft train --config configs/flint.yaml --stage warmup --device cuda \
  --steps ... --corpus runs/corpus/train_tokens.json --out runs/warmup

# Stage 1 — mining (live teacher on this box; off-hours)
#   built corpora: tier-5 512k NIAH documents included; see
#   ksdraft/data — target tokenizer wiring is part of the MI100 session

# Stage 2 — drafter distillation (dual-source conditioning + transfer-space
# loss + top-k CE on teacher support)
ksdraft train --config configs/flint.yaml --stage distill --device cuda \
  --corpus runs/corpus/train_tokens.json --out runs/distill

# Stage 7 — gates + export
ksdraft gate  --config configs/flint.yaml --checkpoint runs/distill/ckpt_XXXXXX.pt --out runs/gate
ksdraft export --config configs/flint.yaml --checkpoint runs/distill/ckpt_XXXXXX.pt --out runs/export
```

The in-process PTQR INT8 teacher (int8-vllm loader) is the MI100-session
integration point: it implements `ksdraft.teacher.TeacherClient` and loads
the deployed Flint PTQR weights (~40 GB INT8, TP4). The FixtureTeacher and
HFTeacher backends run the identical pipeline on the dev box.

## Known boundaries (honest)

- **Rosa credits are CPU/float64** (the exact engine; CUDA tensors incur
  transfers). Correct and exact — not yet GPU-throughput. The GPU-native
  credit kernel is the follow-up workstream; until then, expect Rosa credit
  time to dominate step time at scale.
- **Divergence from reference arithmetic, by decision**: GS128 (vs GS32),
  fp16 warp scalars and fp16 warp intermediate in KS3's int8 mode, INT8
  backward GEMMs with FP16 gradient handoff (Section 8). All are documented
  and parity-tested against the references.
- **Float-exception doctrine**: measured exceptions stay floating and every
  dtype change on a draft surface passes the acceptance gate (±1pt at
  TP4/C12) before adoption — same rule as the fork.
